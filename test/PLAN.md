# 测试计划

这份计划是测试的唯一依据。它规定 `serve` 必须做到什么、怎样判定、覆盖哪些情况。

- **与 README 独立**：README 是给用户看的说明，可以为了好读而简略；测试不引用它。两者
  描述不一致时，不自动以任何一方为准，而是报告出来，由维护者决定改哪一边。
- **与 `serve` 的实现独立**：条目描述的是从外部能观察到的行为，不规定实现方式。
- **每个条目都有编号**，写成"必须 / 不保证"加上可判定的界限。[`spec.py`](spec.py) 里的
  每个 case 都引用它检验的编号。[`run.py`](run.py) 每次运行前会做双向检查：计划里的每个
  编号至少有一个 case；每个 case 引用的编号都在计划里。任何一边对不上，这次运行直接
  失败。

## 1. 范围

要验证两件事：

- **业务正常**：参数、依赖、启动、输出、文件服务、公网隧道及其地址、多实例都按下面的条目工作。
- **不留孤儿进程**：`serve` 以任何方式结束，它启动的进程都不能在它之后继续运行（见第 4 节
  的精确定义）；并且它从不影响自己以外的进程。

不在范围内：Caddy 本身的 HTTP 实现细节、Cloudflare 服务是否可用、性能。

## 2. 术语

| 术语 | 含义 |
| --- | --- |
| 服务 | Caddy 和（`--share` 时的）cloudflared |
| 辅助命令 | `serve` 运行的 `scutil`、`lsof`、`ps` 和（`--share` 时的）`curl` |
| 疑似残留 | 命令行和 `serve` 启动服务时的一样（`caddy file-server --browse --listen :0`，或 `cloudflared tunnel --url http://localhost:<端口>`，前面可以带路径），并且父进程是 launchd（PID 1）的进程 |
| 后代 | `serve` 直接或间接启动的所有进程：服务、辅助命令，以及它们再启动的进程 |
| 管道同伴 | shell 和 `serve` 放在同一个作业里的其他命令，如 `serve \|& tee log` 里的 `tee`。它们和 `serve` 同一个进程组，但不是它的后代 |
| 启动完成 | `serve` 打印出 `Local:` 行的时刻 |
| 公网地址 | 本实例的 cloudflared 在自己日志里给出的隧道地址（`https://<主机名>`），也就是它在本机的 metrics 端口上用 `/quicktunnel` 报告的主机名。同一台机器上别的进程（包括别的 cloudflared）报告的地址都不是 |
| 可用的主机名 | 只由字母、数字、`-` 和 `.` 组成、不超过 253 个字符的主机名 |
| 停止事件 | 终端上的 `Ctrl-C`、`Ctrl-\`，关闭终端，或单独发给 `serve` 的停止信号：`INT` `HUP` `TERM` `QUIT` `PIPE` `ALRM` `USR1` `USR2` `VTALRM` `PROF` `XCPU` `XFSZ` `ABRT` `EMT` `SYS` |
| 致命信号 | `SIGKILL`，以及 `SEGV` `BUS` `ILL` `FPE` `TRAP` |
| 受覆盖的结束 | 不是由致命信号造成的结束 |
| 服务表现 | 服务被要求停止时的表现，分三种：**空闲**（第一个信号就退出）、**传输中**（有下载在传，要重复的信号才立即退出）、**顽固**（无视一切可捕获的信号，只有 `--share` 时才用得上） |

## 3. 业务条目

### 参数

- **ARG-1** `-h`、`--help`：把以 `usage: serve [--share]` 开头的用法写到 stdout，退出码 0，
  不运行任何辅助命令，也不启动服务。
- **ARG-2** 其他任何未知参数：把 `serve: unknown option: <参数原文>` 写到 stderr，参数原文
  原样输出（不解释转义），退出码 2，不运行任何辅助命令，也不启动服务。
- **ARG-3** 参数从左到右处理，`--help` 和未知参数谁先出现就由谁决定结果。
- **ARG-4** `--share` 可以重复写，效果和写一次相同。
- **ARG-5** 不带 `--share` 时不启动 cloudflared，也不要求安装 cloudflared。

### 启动前检查

- **DEP-1** 依次检查 `caddy`、`cloudflared` 和 `curl`（这两个仅 `--share`）、`scutil`、`lsof`、`ps` 是否存在。缺哪个，
  就把 `serve: <命令> not found` 写到 stderr，退出码 1，在 0.5 秒内结束，不运行任何辅助命令。
- **LEAD-1** `serve` 不是进程组组长时（例如 `true | serve`，或在没开 job control 的脚本里被
  当作普通命令调用），打印 `serve: not a process group leader, refusing to start`，退出码 1，
  不启动服务。
- **LEAD-2** `serve` 替换了一个本身是组长的进程时（例如 `zsh -c` 的最后一条命令），可以
  正常运行，也能被 `TERM` 正常停止，退出码 0。

### 输出与服务

- **OUT-1** stdout 上先是一个空行，加上一个四行的块：含有 `serve` 字样的上边框、
  `  Serving: <当前目录的绝对路径>`、`  Local:   <地址>`、下边框。不带 `--share` 时，
  stdout 上只有这些；带 `--share` 时，之后只可能再有 PUB-1 的汇总块。服务和 cloudflared 的
  日志只出现在 stderr 上。
- **OUT-2** stdout 是终端时，`Serving:` 行和 `Public:` 行是红色粗体（`ESC[1;31m`）；不是
  终端时，stdout 上不带任何控制序列。
- **OUT-3** `Local:` 的地址是 `http://<LocalHostName>.local:<端口>/`。读不到 LocalHostName 时
  改为 `http://localhost:<端口>/`，并在同一行注明 `LocalHostName is not set`。
- **OUT-4** `--share` 时，cloudflared 日志里的隧道地址原样出现在 stderr 上。
- **NET-1** 恰好启动一个 Caddy。`Local:` 里的端口，就是它唯一的监听 socket 的端口，而且
  这个 socket 监听所有网络接口（`*:<端口>`）。
- **NET-2** 通过 `127.0.0.1`、`[::1]` 和 `Local:` 里的主机名，都能取到当前目录里文件的
  正确内容。
- **NET-3** 访问目录时返回文件列表，列表中包含点文件。
- **TUN-1** `--share` 时，恰好启动一个 cloudflared，它转发的目标地址（`--url`）指向本实例
  的端口，并且从这个地址能取到当前目录的正确内容。
- **WARN-1** 启动服务之前，只要存在疑似残留，就在 stderr 上打印一个警告块，列出每个
  疑似残留的 PID、进程组和命令行，以及每个进程组的清理命令 `kill -KILL -<进程组>`。
  `serve` 不结束、不向它们发送任何信号，照常启动。
- **WARN-2** 不属于疑似残留的进程不出现在警告里：父进程还在的进程（例如另一个正在运行
  的 `serve` 实例的服务）、命令行不同的进程（例如参数不同的 `caddy`）。
- **TUN-2** 使用真实 cloudflared 时，PUB-1 打印的地址和 cloudflared 日志里的隧道地址相同，
  并且能在 90 秒内从它访问到当前目录的正确内容。

### 公网地址

- **PUB-1** `--share` 时，cloudflared 报告出公网地址后 1 秒内，`serve` 在 stdout 上写出
  一个空行，加上一个五行的汇总块：含有 `serve` 字样的上边框、和 OUT-1 相同的 `Serving:`
  行与 `Local:` 行、`  Public:  https://<主机名>/`、下边框。地址就是本实例的公网地址；cloudflared 过一段时间才报告时（例如几秒后），也照样
  写出。整个运行期间只写一次。
- **PUB-2** 同时运行多个 `--share` 实例时，每个实例写出的都是自己的公网地址。本机上另有
  进程在 cloudflared 优先尝试的 metrics 端口（`127.0.0.1:20241`–`20245`）上用同样的方式
  报告别的地址时，也不受影响。
- **PUB-3** cloudflared 启动后 30 秒内一直读不到可用的主机名时（metrics 端口一直没打开、
  `/quicktunnel` 返回 404、返回的不是预期格式、主机名为空、主机名含有不允许的字符），
  `serve` 在 cloudflared 启动后 30.0–31.5 秒之间把
  `serve: could not read the public address; look for it in cloudflared's log` 写到 stderr，
  不写 PUB-1 的汇总块，也不写出读到的任何内容；之后继续服务，`Ctrl-C` 按 STOP-1 结束。
- **PUB-4** 等待公网地址期间发生停止事件时，结果与 STOP-1 相同，按 CLEAN-1 的时限结束。
- **MULTI-1** 可以同时运行多个实例，端口互不相同；停掉其中一个，其余实例照常服务。

### 读端口

- **PORT-1** Caddy 在启动后 10 秒内一直没有可读的监听端口时（包括 `lsof` 输出非数字、
  0、超出 65535、超长数字、空输出、`lsof` 失败），`serve` 在启动后 10.0–11.5 秒之间结束，
  打印 `serve: could not read the port caddy is listening on`，退出码 1，不启动 cloudflared。
- **PORT-2** Caddy 在监听之前就退出时，`serve` 在 2 秒内结束，打印
  `serve: caddy failed to start`，退出码 1，不启动 cloudflared。
- **PORT-3** 等端口期间发生停止事件时，`serve` 在 1 秒内结束，不打印 `Serving:`，不启动
  cloudflared，退出码 0。

## 4. 停止与进程条目

### 停止事件与退出码

- **STOP-1** 启动完成后发生任何一个停止事件，`serve` 都会收尾并结束，结束时间见 CLEAN-1
  到 CLEAN-3。退出码为 0；服务顽固时为 137。
- **STOP-2** 同样的信号（`TERM` `INT` `HUP` `QUIT`）发给 `serve` 的整个进程组时，结果与
  STOP-1 相同。
- **STOP-3** 启动 `serve` 的 shell 被 `SIGKILL` 时（无论它是不是会话首进程），`serve` 都会
  收尾并结束，结束时间见 CLEAN-1 到 CLEAN-3。
- **STOP-4** 启动阶段（等端口时）父 shell 死亡，视同停止事件：`serve` 按 CLEAN-1 的时限
  结束，不打印 `Serving:`，不启动 cloudflared。
- **STOP-5** 某个服务在运行中退出时，`serve` 打印 `serve: caddy exited` 或
  `serve: cloudflared exited`，收尾并结束，退出码 1（剩下的服务顽固时为 137）。

### 启动前的信号

- **PRE-1** 启动过程中、服务还没开始启动时发生停止事件，`serve` 在 0.5 秒内结束，退出码为
  128 + 信号编号（`Ctrl-C` 是 130，`Ctrl-\` 是 131），不启动任何服务；`serve` 当时正在等待
  的辅助命令（如 `scutil`）也随之结束。

### 暂停与其他信号

- **PAUSE-1** `Ctrl-Z` 让 `serve` 和它的服务一起暂停；`fg` 后恢复运行、继续服务，之后
  `Ctrl-C` 按 STOP-1 结束。暂停期间父 shell 被杀（无论是不是会话首进程），`serve` 都会收尾
  并结束，结束时间见 CLEAN-1 到 CLEAN-3。
- **PAUSE-2** 单独发给 `serve` 的 `TSTP` `TTIN` `TTOU` `STOP` 只暂停 `serve` 本身，服务继续
  对外服务；`CONT` 让 `serve` 恢复，之后 `Ctrl-C` 按 STOP-1 结束。启动阶段收到时，恢复后
  照常完成启动。
- **PAUSE-3** 单独发给 `serve` 的 `CHLD` `WINCH` `URG` `IO` `INFO` 没有任何影响。

### 输出管道

- **PIPE-1** stdout 接到一个在 `serve` 写出 OUT-1 的块后就退出的读端时（如 `| head -2`），
  不带 `--share` 的 `serve` 继续运行和服务，之后 `Ctrl-C` 按 STOP-1 结束。带 `--share` 时，
  `serve` 写 PUB-1 的汇总块时才发现读端已退出，于是收尾并结束：从 cloudflared 报告出公网地址
  算起 2 秒内结束，退出码 0，stderr 上有 `write error: broken pipe`。
- **PIPE-2** stdout 的读端在 `serve` 写入之前就已退出时（如 `| true`），`serve` 在启动后
  2.5 秒内收尾并结束，退出码 0，stderr 上有 `write error: broken pipe`。
- **PIPE-3** stdout 和 stderr 的读端都已退出时（如 `|& true`），`serve` 在启动后 2.5 秒内结束，
  退出码为 0 或 1（取决于 `serve` 和服务谁先写）。
- **PIPE-4** 只有服务的输出接到已退出的读端、而服务先写入时，`serve` 在启动后 3.5 秒内结束，
  退出码 1。

### 收尾时限

时间都从停止事件发生时算起，到 `serve` 结束为止；`serve` 的结束时刻以启动它的 shell
报告的时间为准。

- **CLEAN-1** 服务空闲时，1 秒内结束。
- **CLEAN-2** 服务传输中时，2 秒内结束，退出码不受影响（仍为 0）。
- **CLEAN-3** 有服务顽固时，在 5.0–6.5 秒之间结束，退出码 137。下界保证顽固的服务至少有
  5 秒的宽限。
- **CLEAN-4** 收尾开始后，再发生任何停止事件，或者 `TERM` `INT` `HUP` `QUIT` 被发给整个
  进程组，或者父 shell 被杀，都不改变收尾的结果和时间（仍按 CLEAN-3）。

### 进程

- **PROC-1 不留孤儿**：受覆盖的结束之后 1 秒内，`serve` 的所有后代（服务和辅助命令）
  都已结束；运行 `serve` 的终端会话里，除了 shell、诱饵进程和管道同伴外，不再有任何
  进程。
- **PROC-2 损害有界**：`serve` 因致命信号结束时（不收尾），留下的进程全部在 `serve`
  原来的进程组里，`kill -KILL -<PGID>` 能在 1 秒内把它们全部清除。退出码为 128 + 信号编号。
- **PROC-3 不误伤**：同一个会话里、不在 `serve` 进程组里的进程（诱饵），以及另一个
  终端里的 `serve` 实例（旁观实例）及其服务，都不会受任何影响。

管道同伴不在 PROC-1 的范围内，它们是否结束既不保证、也不要求。要求它们结束，就等于要求
`serve` 在退出时结束用户管道里的其他命令，这本身就是一种副作用：例如 `serve 2>&1 | less`
停止后，`less` 也就没法再翻看了。现在 `serve` 按进程组发信号，确实会顺带发到它们身上：
这是选择"只对自己的进程组发信号"这个方案时接受的取舍，是副作用，不是刻意保证的行为，
测试也不检查管道同伴有没有被结束。

### 已知的非保证

以下情况 `serve` 不保证正常结束，但结果必须如下，测试照此检验：

- **LIM-1** `lsof` 卡住时（测试里 30 秒不返回），`serve` 在 12 秒后仍未结束，也不打印 `Serving:`；按 `Ctrl-C` 后
  正常收尾，退出码 0。
- **LIM-2** `scutil` 卡住时（测试里 30 秒不返回），`serve` 在 2 秒后仍未启动任何服务；按 `Ctrl-C` 后结束，
  退出码 130。
- **LIM-3** 收尾过程中 `serve` 被 `SIGKILL` 时，按 PROC-2 处理，退出码 137。
- **LIM-4** `--share` 时，读公网地址用的 `lsof` 卡住（测试里 30 秒不返回），`serve` 照常
  服务，不写 PUB-1 的汇总块；按 `Ctrl-C` 后按 STOP-1 正常收尾，退出码 0。

## 5. 判定方法

- **会话**：每个 case 在自己的伪终端里运行，它就是一个独立的会话。会话成员由内核直接
  判定（`getsid`），不做采样。
- **账本**：`serve` 的 PATH 里只有记账垫片，辅助命令和服务在 exec 真正的程序之前，先
  登记 PID、父进程和参数。垫片只用 shell 内建命令，不能拖慢 `serve`（`serve` 等端口时
  每秒要运行十次 `lsof`）。夹具第一次在本 case 的会话里看到某个登记的进程时，记下它的
  启动时间，此后只有启动时间对得上才算是它；从没看到过的（几毫秒就结束的辅助命令），
  只有还在本 case 的会话里才算。
- **`serve` 本身**：启动它的 shell 的子进程中，自己带领一个进程组、又不是诱饵的那一个。
- **替身不会永远卡住**：模拟"卡住"的替身实际运行 30 秒，比所有时限都长。`serve` 没有按
  预期结束它，就会作为残留被发现、判为失败；但无论如何，测试本身不会跟着卡住。
  cloudflared 替身和诱饵进程也都只存活有限的时间（5 分钟），测试异常中断时也不会在
  机器上长期残留。
- **诱饵**：每个 case 从同一个 shell 启动一个忽略 `SIGHUP` 的 `sleep`，它和 `serve` 同会话、
  不同进程组，用来检验 PROC-3。
- **旁观实例**：整轮运行开始前启动一个 `serve --share`，每个 case 结束后检查它的进程和
  服务都还在（PROC-3）。
- **计时**：`serve` 的结束时刻由启动它的 shell 在同一行命令里报告，不依赖夹具的轮询。
  没有 shell 能报告时（终端已关闭、父 shell 已死），才用轮询的结果。
- **公网地址的计时**：cloudflared 的启动时刻取内核记录的进程创建时间；地址的就绪时刻
  由 cloudflared 替身在打开 metrics 端口之前记下。两者都不会比实际晚，所以测出的时长
  不会偏短。
- **退出码**：同样由 shell 报告；前台作业被 `SIGINT` 杀掉时，shell 会放弃同一行剩下的
  命令，这时改为另起一行查询。
- **时限的宽容**：所有时间上界统一放宽 0.5 秒，与并行数无关；下界不放宽。实测 6 路并行
  并不比串行慢（见第 10 节）。
- **系统卡顿探针**：夹具记录每个 case 里自己等待循环的最长间隔。这个循环每 20–100 毫秒
  转一次，间隔远大于此说明整台机器卡住了。计时失败时报告会附上这个值，用来区分是
  `serve` 慢，还是环境卡顿。
- **计时失败不一定是代码的问题**：计时失败一律判为失败，不自动重跑。但整机偶尔会卡顿
  （第 10 节），超时也可能由此造成。所以计时失败的报告会附上提醒和卡顿探针的数值；
  判断之前，先看探针，必要时单独重跑那个 case。

## 6. Case 矩阵

条目适用的所有组合都要覆盖：

| 维度 | 取值 |
| --- | --- |
| 模式 | 局域网、`--share` |
| 事件发生的阶段 | 服务启动前、等端口时、等公网地址时（仅 `--share`）、运行中、收尾中、无事件 |
| 事件 | 第 2 节的全部停止事件；发给进程组的 `TERM` `INT` `HUP` `QUIT`；父 shell 被杀（会话首进程 / 嵌套 shell）；服务被 `SIGKILL`；`Ctrl-Z` 及其后续；PAUSE-2、PAUSE-3 的全部信号；全部致命信号 |
| 服务表现 | 空闲、传输中；`--share` 时另加顽固 |

WARN-1、WARN-2 另有专门的 case：夹具自己造出几个"父进程已不在"的假进程，命令行分别和
疑似残留一致或不一致，再加上一个正在运行的 `serve` 实例，检查警告列出了该列出的、没有
列出不该列出的，并且那些假进程都没有被动过。检查只针对夹具自己造的这些进程，所以机器
上本来就有的残留不会让它误判。

每个 case 除了检查它引用的条目，还自动检查 PROC-1（或 PROC-2）和 PROC-3；运行中阶段的
case 还会在事件发生前检查 OUT-2、OUT-3、NET-1 到 NET-3，以及 `--share` 时的 TUN-1 和
PUB-1（地址对不对；1 秒的时限由专门的 case 检查）。

PUB-2 由多实例的 case 检查：夹具先在 20241–20245 里最小的空闲端口上放一个假的 metrics
服务，报告一个假地址，再同时启动几个 `serve --share`，检查每个实例写出的都是它自己那个
cloudflared 日志里的地址。

## 7. 夹具自检

测试通过，不代表夹具能发现问题。所以夹具每次改动之后，都要做一次性检查：拿当时那一版
`serve` 临时做几个故意改坏的副本，每个副本对应夹具要检查的一类问题，再用
`run.py --serve 副本路径` 确认相应的 case 会失败。副本和检查都是一次性的，用完就丢，
不保存。产品迭代之后，基线已经变了，旧的副本也就不再有意义。

## 8. 变更规则

- **不迁就当前实现**：测试测出 `serve` 不符合本计划，说明测试起作用了，要改的是 `serve`。
  不能为了让现在的 `serve` 通过而修改计划或夹具。
- **只修夹具自身的问题**：夹具观察有误时（例如没读终端、读到过期的退出码、替身和真实
  程序行为不一致），可以修夹具，但不能放宽任何预期，每一处这样的修改都要单独说明。
- **计划本身要改时**，先由维护者决定，再同步修改 `spec.py`。双向覆盖检查保证两者不会
  各改各的。

## 9. 已确认的决定

维护者 2026-09-29 确认：

1. **PROC-1 的范围**：辅助命令算在内（它们是 `serve` 的后代，要求它们结束没有副作用）；
   管道同伴不算（理由见 PROC-1 下的说明）。
2. **偏实现层面的检查**：只判断"是否用了某种特定实现"的检查没有意义，删去；有价值的
   改为检验外部行为。因此删去了 NET-4（进程组和会话归属：出错时 PROC-1、STOP 等行为
   检查自然会失败）、Caddy 的具体启动参数，以及 cloudflared 参数必须写成 `localhost`；
   TUN-1 改为检验转发目标能取到正确内容。
3. **整机卡顿时的计时失败**：维持一律判失败，但在报告里提醒失败可能来自卡顿（第 5 节）。
4. **`serve` 本身被强制杀死**（`SIGKILL`、`SEGV` 等）：维持为已知限制，按 PROC-2 检验。
5. **`Serving:` 行在终端上和服务日志交错**：本计划不作要求，OUT-1 只对 stdout 本身的内容
   提要求。后来 `serve` 改为一次写出带边框、前置空行的块，这个问题在实际使用中已基本
   避免，README 不再把它列为已知限制。
6. **`lsof` 卡住时 10 秒上限不起作用**：维持现状，作为已知限制，按 LIM-1 检验。
7. **疑似残留的提示**：`serve` 启动前只提示、不处理（WARN-1、WARN-2），由用户判断和清理。
8. **公网地址**（2026-09-29）：`--share` 时 `serve` 把公网地址写进自己的输出（PUB-1 到
   PUB-4）。地址向本实例的 cloudflared 询问（它 metrics 端口上的 `/quicktunnel`），不解析
   日志；读不到时只提示、照常服务。`--share` 的 `serve` 在启动后还会再写一次 stdout，
   所以提前退出的读端会在那时被发现（PIPE-1）。读地址用的 `lsof` 卡住时的情况作为已知
   限制（LIM-4），和 LIM-1 同理。

## 10. 时间界限的来历

每个界限都先按 `serve` 的机制和使用上的要求定出目标，再用实测确认目标可行、看噪声
有多大。实测值只用来验证，不直接拿来当界限。实测数据来自 2026-09-29，同一台 Mac 上
各跑一轮串行和 6 路并行，覆盖全部 335 个不会让进程崩溃的 case。

| 条目 | 界限 | 依据 | 实测（串行 / 6 路并行，最大值） |
| --- | --- | --- | --- |
| DEP-1、PRE-1 | ≤ 0.5 秒 | 什么都还没运行，或 trap 立即生效 | 0.05 / 0.10 |
| PORT-1 | 10.0–11.5 秒 | 截止时间从 Caddy 启动时算起，所以不会早于 10 秒；之后最多再跑一轮 `lsof` | 10.60–12.07 / 10.59–11.08 |
| PORT-2 | ≤ 2 秒 | 一轮 `lsof`（真实的 `lsof` 扫描要几百毫秒） | 1.52 / 1.29 |
| PORT-3、STOP-4 | ≤ 1 秒 | 等端口的循环每轮都检查 | 0.54 / 0.70 |
| CLEAN-1（含 STOP-3 的嵌套 shell） | ≤ 1 秒 | 主循环每 0.5 秒检查一次，服务收到 `TERM` 后约 0.2 秒内退出 | 0.69 / 0.70 |
| CLEAN-2 | ≤ 2 秒 | 0.5 秒 + 约第 0.9 秒的第二轮补发信号 + 约 0.2 秒 | 2.98 / 1.68 |
| CLEAN-3、CLEAN-4 | 5.0–6.5 秒 | 50 轮、每轮至少 0.1 秒，加上察觉停止最多 0.5 秒 | 5.57–6.05 / 5.66–5.92 |
| PIPE-2、PIPE-3 | ≤ 2.5 秒 | Caddy 启动加打印 | 1.54 / 1.45 |
| PIPE-4 | ≤ 3.5 秒 | 另加替身 1 秒后才写的那条日志 | 2.20 / 2.38 |
| PUB-1 | ≤ 1 秒 | 主循环每 0.5 秒检查一次，加一轮 `lsof`（几百毫秒）和一次本机 `curl`（几毫秒） | — / 0.76 |
| PUB-3 | 30.0–31.5 秒 | 截止时间从 cloudflared 启动时算起，所以不会早于 30 秒；之后最多再跑一轮（0.5 秒，加上 `lsof` 和最多 1 秒的 `curl`） | — / 30.11–30.48 |
| PIPE-1（`--share`） | ≤ 2 秒 | PUB-1 的 1 秒，加上收尾（CLEAN-1）的 1 秒 | — / 1.39 |

PUB-1、PUB-3 和 `--share` 的 PIPE-1 是后来（同一天）加的，只有一轮全量 6 路并行的数据。
另外单独运行这几个 case 时，测得 PUB-1 最大 0.79 秒、PUB-3 在 30.02–30.52 秒之间、
PIPE-1 1.38 秒，都在界限内。
| PROC-1、PROC-2 | 1 秒 | 停止后，组里剩下的进程收到 `TERM`/`KILL` 立即结束，没有要等的东西 | 2.43 / 0.24 |

超出界限的只有串行那一轮里的 6 个孤立样本：CLEAN-2 一个（2.98 秒）、PORT-1 一个
（12.07 秒）、PROC-1 四个（最大 2.43 秒）。它们分散在不同的 case 里，没有共同点，
负载更重的并行那一轮也没有出现，看起来像偶发的整机卡顿，但当时还没有卡顿探针，
无法确认。这些样本没有被用来放宽界限。
