# 测试

端到端测试。用真实的 `caddy`，在伪终端里驱动交互式 zsh 运行 `serve`，逐条检验
[测试计划](PLAN.md)。测试计划是测试的唯一依据，独立于项目的 README 和 `serve` 的实现。

```bash
python3 test/run.py                   # 全部 case，cloudflared 用本地替身
python3 test/run.py -k lsof -k pretrap # 只跑 id 里含这些字样的 case
python3 test/run.py --list            # 列出全部 case 和它们检验的计划条目
python3 test/run.py --real-tunnel     # 只跑少数几个需要真实隧道的 case
python3 test/run.py --serve 某个脚本   # 测别的脚本，比如故意改坏的副本
```

前提：macOS，`caddy` 在 PATH 上。只有 `--real-tunnel` 需要 `cloudflared`。默认 6 路并行，
可以用 `-j` 调整。

## 四个文件

- **[`PLAN.md`](PLAN.md)：测试计划。** 规定 `serve` 必须做到什么（带编号的条目和具体
  界限，包括"不留孤儿进程"的精确定义）、怎样判定、覆盖哪些情况，以及变更规则。
- **[`spec.py`](spec.py)：每个 case 应该发生什么。** 每个 case 都引用它检验的计划条目
  编号。计划里列举的东西（信号、停止事件、依赖命令、参数）整张表拿来，再和它适用的
  每种组合做笛卡尔积：
  - 运行模式：局域网 / `--share`；
  - 事件发生的阶段：启动前、等端口时、运行中、收尾中；
  - 子进程的表现：没有请求在传 / 有下载在传 / 无视一切信号。
- **[`fixture.py`](fixture.py)：观察 `serve` 实际做了什么。**
- **[`run.py`](run.py)：执行 case、比对结果、汇总报告。**

## 计划和 case 保持一致

`run.py` 每次运行前，都会核对 `PLAN.md` 和 `spec.py`：计划里的每个条目都至少有一个
case 检验；每个 case 引用的条目都在计划里。有一边对不上，运行就直接停止，并列出
问题。所以计划和 case 不会各改各的。

修改计划、修改夹具时的规则见 [`PLAN.md` 第 8 节](PLAN.md#8-变更规则)。最重要的一条：
测试测出 `serve` 不符合计划，要改的是 `serve`，不能为了让它通过而改计划或夹具。

## 怎样判定"没有留下进程"

夹具如果漏看一个进程，就会报告一次"干净"的运行，而那次运行其实并不干净。所以判定
依据是两份互相独立、没有时间窗口的记录：

- **会话**：每个 case 在自己的伪终端里运行，也就是一个独立的会话。`serve` 启动的
  一切，以及它们再启动的一切，都留在这个会话里，除非自己调用 `setsid()`。会话成员由
  内核直接回答（`getsid`），不需要采样进程树，短命的进程也漏不掉。case 结束时，
  会话里只允许剩下 shell 和诱饵进程。
- **账本**：`serve` 的 PATH 里只有"账本垫片"。`caddy`、`cloudflared`、`lsof`、`scutil`
  先把自己的 PID、父进程和参数记下来，再用同一个 PID exec 成真正的程序。所以
  `serve` 运行过的一切，在它能做任何事之前就已经记录在案。垫片只用 shell 内建命令：
  它们每次都在 `serve` 的执行路径上，如果调用 `ps`，系统一卡顿就会把 `serve` 本身拖慢，
  那就是夹具在干扰被测对象。进程的启动时间由夹具在第一次看到它时记下，此后只有
  启动时间对得上，一个 PID 才算是记录里的那个进程，所以 PID 复用既伪造不出泄漏，
  也伪造不出干净退出。

除了 case 自己的预期，每个 case 结束时还要满足：

- 账本里没有任何进程还在运行；
- 会话里只剩 shell、诱饵进程和管道同伴（管道同伴不在"不留孤儿"的要求之内，理由见
  计划的 PROC-1）；
- 诱饵进程还活着。诱饵和 `serve` 从同一个 shell 启动，同会话、不同进程组，并且忽略
  `SIGHUP`，用来证明 `serve` 没有把信号发到自己的进程组以外。

整轮运行期间，还有一个在所有 case 之前启动的旁观 `serve` 实例，每个 case 之后都要
确认它没受影响。计划允许留下进程的情况（PROC-2），要求留下的恰好是 `serve` 原来
的进程组，并且 `kill -KILL -<PGID>` 能清干净。

## 夹具自身必须遵守的几条

这些都是踩过的坑：

- **终端必须一直有人读。** 没人读的终端写满以后，往里写的一方就会卡住：写日志的
  服务、正在打印的 `serve`，或者正在退出、要先把输出冲刷掉的 shell。这样的 shell
  永远退不完，内核也就不会把它的作业当作孤儿处理，夹具就会报告一个真实终端里根本
  不会出现的泄漏。所以夹具里的每一次等待，都会同时读取所有打开的终端。
- **退出码另起一行查询。** 前台命令被信号杀掉时，交互式 shell 会放弃同一行剩下的
  命令。
- **进程结束的时刻由 shell 报告。** 启动 `serve` 的那一行命令，末尾就让 shell 在
  `serve` 结束的那一刻打印时间戳和退出码。夹具轮询进程时可能会被系统调度拖慢好几秒，
  用轮询到的时间去判断"是否按时结束"会误报。
- **case 怎么结束都要清理。** 不论 case 怎样结束，都会杀掉它会话里的所有进程。
  整轮结束后再按所有用过的会话扫一遍，扫到的算作夹具自身的残留，单独报告，并让
  这一轮失败。

## 检验夹具本身

测试通过，不代表夹具真的能发现问题。夹具每次改动之后，拿当时那一版 `serve` 临时做
几个故意改坏的副本，用 `--serve` 指向它们，确认相应的 case 会失败。这些副本只用来
一次性检查这一次改动，用完即弃：产品迭代之后基线就变了，旧副本没有意义。做法见
[计划第 7 节](PLAN.md#7-夹具自检)。

## 副作用：崩溃报告

测试计划要求检验 `serve` 在致命信号 `SEGV`、`BUS`、`ILL`、`FPE`、`TRAP` 下的表现
（PROC-2），以及启动前收到 `ABRT`、`EMT`、`SYS` 的表现（PRE-1）。测试会真的把这些信号
发给 `serve`，让 zsh 按默认动作崩溃；启动前按 `Ctrl-\` 的 case 还会让夹具里的 shell 垫片和 `sleep` 跟着
崩溃。macOS 会为每次崩溃运行 ReportCrash，在 `~/Library/Logs/DiagnosticReports` 里
生成崩溃报告：`zsh-*.ips`、`bash-*.ips`（`/bin/sh` 实际运行的是 bash）、`sh-*.ips`、
`sleep-*.ips`。每跑一次全套大约新增几十个。

**跑完测试后，请手动清理这些报告。** 测试脚本不会自动删除，因为做不到既完整又
安全：

- **报告可能很晚才写出来**：大多数报告在崩溃的同一秒就写好了，但实测有的在二三十
  分钟之后才出现（最长约 28 分钟）。测试运行结束时，没办法知道报告是否已经写全。
- **不是每次崩溃都有报告**：ReportCrash 会限流。
- **同名报告也可能是你自己的**：同一个目录里，你自己的 zsh、bash、sh、sleep 真的崩溃
  时，生成的报告名字完全一样。只有人能判断哪些是测试产生的。

测试结束时会打印这次运行的起止时间。建议等半小时左右再清理，先用下面的命令列出
这段时间以后写入的相关报告，逐个确认后再删除或移到废纸篓。这条命令只列出，不删除：

```bash
find ~/Library/Logs/DiagnosticReports -newermt '运行开始时间，如 2026-09-29 02:10' \
  \( -name 'zsh-*.ips' -o -name 'bash-*.ips' -o -name 'sh-*.ips' -o -name 'sleep-*.ips' \)
```

**不清理会怎样**（2026-09-29 在一台 Mac 上观察到的情况，不是文档写明的规则）：

- **macOS 看起来会自动清掉旧报告**：这个目录里没有 7 天以前的报告，而那台机器明显用了
  更久；还有一个空的 `Retired` 子目录，符合"先归档、再删除"的做法。但系统分析配置里
  没有找到崩溃报告的保留期限，系统日志里也没有清理记录，所以期限和规则都不确定。
- **占用很小**：每个报告约 8 KB，跑一次全套约几百 KB。
- **是否发送给 Apple 取决于系统设置里的"共享 Mac 分析数据"**：那台机器没有开启。

所以不清理大概也无妨，主要影响是控制台（Console）的崩溃报告列表会变得杂乱。但为了
保持干净，仍然建议跑完后按上面的方法手动清理。

崩溃报告程序介入期间，读取所有进程命令行的 `ps` 会被卡住好几秒，创建进程也会变慢。
真实使用 `serve` 时不会碰到这种干扰，它完全是测试自己制造的。所以：

- 夹具的日常轮询不读命令行；
- 会让进程崩溃的 case（`spec.py` 里标了 `crashes=True`）放在最后单独、逐个运行，
  不和其他 case 并行。

这只影响执行顺序，不改变任何 case 的预期。

## cloudflared 替身

Cloudflare 对 quick tunnel 有频率限制，全量运行要启动几百次隧道，所以默认用一个
本地替身。替身按真实 cloudflared 的方式对待信号，这些行为已对照真实程序确认：

- 被忽略的 `SIGINT` 会被重新启用；
- 第一个 `TERM`/`INT` 开始优雅关闭；
- 之后不再处理信号：`SIGINT` 回到忽略，再来一个 `TERM` 就按默认动作结束；
- 往断掉的管道写日志时被 `SIGPIPE` 结束。

`--real-tunnel` 只跑三个 case，用真实隧道检验隧道地址、隧道内容，以及通过隧道下载
途中停止的情况。

## 计时失败怎么看

计时失败一律判为失败，但整台机器偶尔会卡顿几秒，这也会造成超时，所以**计时失败不一定
代表 `serve` 有问题**。每条计时失败都附有这个 case 里夹具等待循环的最长间隔：正常只有
0.1 秒左右，远大于此说明当时整机卡住过。拿不准时，用 `-k` 单独重跑那个 case。
